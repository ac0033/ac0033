# 让 Agent 可靠地干活：从单 Agent 到多 Agent，再到 AI OS

观点和思考：YuanLumen  
撰稿：[写作管道](https://github.com/ac0033/writing-agent/blob/main/README.md)  
润色：Codex。

让 Agent 可靠地干活，需要同时建设模型能力和围绕模型的运行机制。随着工作范围扩大，这件事会自然展开成三个层次：先让一个 Agent 根据真实材料行动，再让多个 Agent 有序分工、交接和纠错，最后让系统主动发现值得做的事，经过验证后交给人决定。这也是本文从单 Agent、多 Agent 编排走向 AI OS 的主线。

以写一篇技术文章为例：最初，我们在聊天窗口请模型解释概念；把模型接进程序后，可以批量处理问答；接上检索和文件工具，它就能找资料、读原文、写稿。当一项任务需要不同职责配合，就可以安排研究、写作和审核角色。当步骤难以预先写全，还需要 Agent 根据结果调整路线。再向前想一步：能否在我提出要求之前，发现关键来源可能失效、重复工作可以合并、某个流程存在隐患，并带着证据提出改进？最后这个问题，是我思考 AI OS 的起点。

这条路线扩大的是系统处理问题和发起行动的范围。单 Agent 解决“怎样把判断变成行动”，多 Agent 解决“怎样让分工成为一项完整工作”，本文的 AI OS 构想解决“怎样主动发现机会，又让改变经过选择与授权”。各层都沿着同样的目标建设：**透明**，让依据和过程可回查；**自动化**，让可重复的工作自行推进；**可控**，让人能够设边界、纠正和叫停；**直观**，让人看懂当前状态并作出决定。下面先从已经实现的项目讲起，再展开尚待验证的 AI OS 设计。

## 第一编：让一个 Agent 的判断、行动和反馈接起来

让模型读一份文件，它要先知道文件在哪里，选择读取工具，拿到内容，再决定下一步。模型之外，必须有程序负责准备材料、执行调用和记录结果。LangChain 的[官方文章](https://www.langchain.com/blog/the-anatomy-of-an-agent-harness)用一个简洁的公开表述概括这层关系：**Agent = Model + Harness**。本文沿用这个理解：Model 是模型；Harness 是模型周围让任务实际运行起来的代码、配置和执行机制。

为了逐项检查这些运行机制，可以进一步写成：

```
单 Agent = Model + Harness
Harness：Context + Tools，以及贯穿其中的预防、检测、恢复
```

Context 是模型这一步收到的上下文，Tools 是它能够调用的工具。上下文与工具之外再加保障机制，也已有公开的同类拆分，例如李博杰的[《深入理解 AI Agent：设计原理与工程实践》第一章](https://github.com/bojieli/ai-agent-book/blob/main/book/chapter1.md)使用“约束、验证、纠正”。本文采用“预防、检测、恢复”来组织后面的项目分析：行动前减少错误进入，行动中检查实际结果，出错后处理和收场。这是对既有工程做法的组织与应用。

这几个部分相互配合。模型依据上下文作判断，工具把判断变成操作，操作结果又回到上下文；保障机制贯穿整个过程。状态记录、循环控制和权限检查也在 Harness 的范围内，不能只把它理解成一份更长的提示词。

### 循环：判断怎样变成行动

把刚才读文件的过程展开，单 Agent 的工作方式就是一个循环：

```
整理上下文 → 模型判断 → 检查并执行工具 → 取得实际结果
     ↑                                      │
     └────────── 更新上下文，继续判断 ────────┘
```

上下文决定模型这一步依据什么来判断。模型据此决定下一步做什么。工具让这个决定变成实际操作——查一份文件、搜索一段资料、写入一条记录。操作的结果回到上下文，供模型继续判断。循环一直推进，直到满足完成条件，或者遇到需要人来决定的事情。

保障机制贯穿这个循环的每一步。行动前，预防机制限制模型能碰什么、不能碰什么；行动中和完成后，检测机制查看结果是否偏离预期；出了错，恢复机制决定是重试、退回、降级还是交还给人。这些安排的目标，是更快发现错误，并缩小错误的影响。

模型选型当然也重要——具体任务上看表现、成本和速度。工程机制可以帮助模型获得材料、调用擅长特定工作的工具，但不能保证任何模型都能完成任何任务。我的关注点在模型之外：怎样把信息组织好，怎样让判断有办法落地，怎样在出错时发现问题、退回或交还给人。

### Context：把模型眼前的信息变成可以整理的工作材料

上下文是模型在这一步实际收到的全部材料。除了用户刚输入的那句话，还可能包括系统给出的要求、之前的对话、读取的文件、工具返回的结果。对话变长以后，这些材料不断积累：重复读取的文件、早已过时的工具结果、试过后不再需要的方案，都可能还留在里面。

聊天窗口能告诉你双方说过什么，却不能回答一个更实际的问题：当前这次请求里到底还有哪些内容，哪些已经没必要继续占着位置？

**dsh-ctm：让上下文可以查看、判断、调整和回查**

我为 DeepSeek Harness 做了一个上下文管理插件，叫 [dsh-ctm](https://github.com/ac0033/dsh-ctm/blob/main/README.md)（Context Transparency Manager）。[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 是外部开源项目，负责 Agent 的基础运行；我在它上面增加上下文视图和编辑能力，让人可以直接查看、判断和调整模型将使用的材料。

它做的第一件事是把混在一起的材料拆开。插件按会话轮次和内容片段展示信息，让用户区分自己输入的要求、系统补充的内容、模型回答和工具结果。需要时可以展开某一段，不必在长对话里反复翻找。重点在于知道一段话从哪里来、在这次任务里起什么作用。

能看到还不够。假设同一份文件被读取了几次，返回内容几乎相同；或者一段很早的工具结果，已经隔了许多轮回答。它们是否还值得占着位置？插件会给内容加上有效、重复、可能过时等提示，也允许用户手动修改这些判断。当前实现参考内容的新旧和文字相似程度，是启发式标记，不是在核验事实，也不能据此认定一份材料已经没有价值。所以提示可以自动给出，最后的取舍留给人。机器先帮忙缩小检查范围，人可以复查和纠正。

另一个容易混淆的问题是消耗。模型这一次收到多少材料，与整个任务至今处理了多少内容，是两本账。一段材料先前已经被模型处理过，现在把它从后续输入中移除，可以影响接下来的请求，却不会让过去的消耗消失。插件分别呈现单次请求和累计用量，区分输入、缓存复用和输出。累计值从完整记录计算，不会因为界面上移除了某些内容就一起减掉。用量的单位是 token，即模型处理文本的计量单位；细到某一个片段的大小只能估算，也会标明是估算。若要据此计算累计费用，还要结合相应模型和缓存的计价，不能把 token 总数直接当成账单。这些数字的用途是帮人理解信息放在哪里、消耗从哪里产生，不是摆出一个看似精确的总数。

再往前一步，是让整理真正影响后续工作。插件提供替换、删除、回退和撤销。界面上的变化必须和模型之后收到的内容对应，因此"实际应用"是一个明确开关，默认关闭。打开后，修改先进入队列，在下一步构建模型请求之前写入记录并生效。对空闲会话的修改，也要等下一步运行。等待中的修改显示为待生效状态，不让人误以为模型已经看到了新版本。

这里有一个不容易从按钮看出来的设计：模型发出的工具调用和工具返回的结果，是一组相互对应的信息。不能只删掉其中一半，留下一个没有结果的调用。插件在移除相关内容时会检查这组关系，必要时把相连的记录作为一组处理。这样整理材料才不会把会话结构弄坏。

修改也不会把过去抹掉。系统通过新的变更记录来改变后续使用的内容，原来的信息仍有历史可查。撤销也有具体边界。尚未生效的修改可以移出队列；已经生效的修改，要用一条新的反向变更恢复，而且只支持撤销最近一次操作。涉及回退或成组删除时，恢复的内容会以用户消息放回，原来的模型或工具角色不会原样复原。它恢复了可供后续使用的内容，但没有倒转已经发生的工具执行。

dsh-ctm 的设计重点，是把可见片段、有效性提示、用量、编辑生效状态和历史记录接到同一份工作材料上。看到冗余提示后，人能展开检查，再决定是否移除，随后确认修改是否生效、是否需要撤销。透明要让人沿着一条线索理解“模型这一步到底读了什么”；直观要让人看完之后能决定下一步怎么做。

**记忆：信息何时进入、何时过时**

上下文解决的是“这一步模型看到什么”，记忆解决的是“跨任务、跨会话的信息怎样积累和维护”。我做的 [agent-memory](https://github.com/ac0033/agent-memory/blob/main/README.md) 是一个本地长期记忆基础设施，不绑定特定 Agent 框架。它把记忆分成三层：

长期记忆存跨任务的经验——用户偏好、项目决策、过去踩过的坑。工作记忆存当前任务的状态——目标、待办、已做的决定、进行到哪一步。短期层读取近期对话记录，不新建文件，只做解析。

这三层需要以不同的方式进入当前上下文。处理手头任务，先看工作记忆里的目标和进度；需要回忆刚才的对话，再读近期记录；遇到相关项目或习惯，才检索长期记忆中的条目。长期保存不意味着每次都全部塞给模型，仍要按相关性和输入预算选择。

信息进入长期记忆库不是无条件的。长期记忆的写入流程先处理可能的敏感内容，再判断是否值得保留，最后与已有记忆对账。同样一项项目决定已经记过，就不必再添一份；新决定取代旧决定，则需要更新；新旧信息冲突又无法判断时，先交给人复核。评价门也会检查明显的指令性内容和低置信度条目。这些规则不能保证识别所有问题，但能避免把每一次模型输出都直接变成长期依据。

信息过时同样需要处理。当一条记忆被更新或删除，依赖旧事实的近邻条目会被检查：是失效、需要修订、还是不受影响。失效的删除留审计日志，需要修订的进复核队列。这套传播机制处理的是“一条信息变了，相关的信息怎么办”，判断结果仍要允许复核。

记忆服务出问题时，还要区分是哪一种问题。写入一条存疑记忆可以被拦下；可选记忆服务暂时不可用，则不必让写作主流程一起停摆。我的写作管道遇到后一种情况会记录警告并继续，只是本次无法获得那部分历史信息。被降级的是辅助能力，文章本身的审核要求仍然保留。

**知识库：来源与笔记分开**

与记忆配合的是 [llm_wiki](https://github.com/ac0033/llm_wiki/blob/main/README.md)，一个 AI Agent 主题的文献知识库。它把内容分成三层：原始素材层逐字保存抓到的 PDF 和网页快照，不做改写；知识层是按主题组织的 Markdown 页面，论断必须能回溯到原始层的一手来源；元数据层存登记簿和配置。

这个分层的意义在于区分来源和理解。一条知识笔记可能综合多篇来源，也可能包含我自己的判断。保留原始材料，后续才能核对“论文实际上说了什么”和“我是怎样理解的”。我还在本地增加了把确认稿件接回知识库的流程：检查对应版本后生成待核验的新笔记，保留草稿身份和登记日期，不覆盖已有条目。这里的登记日期只表示何时入库，不能把旧资料变成新事实。这个衔接实现与公开知识库的基础分层需要分开看。

### Tools：让判断有办法变成行动

模型做出了判断，接下来需要执行。工具就是这个接口：搜索一段资料、读取一个文件、调用一个服务。

每个工具需要清楚的用途说明、参数定义、返回格式、错误处理和权限范围。在我的写作管道里，检索工具让不同节点查不同的知识来源：定框架和写初稿的节点查知识库，润色节点查素材库。记忆服务通过标准接口暴露搜索、写入、反馈等操作。技能规范告诉 Agent 怎么做一件事，工具提供实际可执行的动作——这是两项不同的工作。

例如定框架时需要弄清上下文管理，节点可以给知识库检索工具一个相关查询。工具返回匹配的笔记片段、文件来源、笔记状态和待核对的外部链接。节点据此定位材料；要把外部说法写进文章，还应读取对应原文。如果没有匹配内容，工具明确返回未检索到；调用出错则记录失败，节点需要换查询、另找来源或保留缺口，不能把空结果说成查证通过。查询、返回、判断和下一步动作，这样才接成了一次完整使用。

还有一点容易忽略：工具的说明文字会进入上下文，成为模型判断的依据；但说明一种能力和真正执行它，是两回事。模型读到"你可以搜索知识库"，和它实际发起一次搜索、拿到结果、处理可能的错误，中间隔着参数校验、权限检查、返回解析这些工程工作。

Anthropic 的[工程经验](https://www.anthropic.com/engineering/building-effective-agents)也把工具说明、输入输出设计和环境反馈列为重要工作。工具开放多少，还要结合任务和风险判断。落实到项目中，学习助手在具体检索路径中限定会话文件范围，记忆写入经过评价和对账，写作发布则需要明确的目标与授权。它们限制的是不同动作，不能只靠一句“请谨慎操作”来替代。

### 三层保障：预防、检测、恢复

回到开头那个循环，三层保障要落实成能执行的检查和处理步骤。

**预防**发生在行动前。我的[学习助手项目](https://github.com/ac0033/learning_assistant_agent/blob/main/src/agent/nodes/document_retrieval.py)用课程材料帮助用户学习和提问，检索是它回答问题前的一步。项目的修复记录里有过一个问题：新对话查询极限知识，却取回旧对话的词向量讲义。文件放在共同索引里，检索路径没有区分会话。修复是在这条路径上使用当前会话的文件白名单，没有可用文件就返回空结果。这个例子说明，即使一段资料与某个词很相关，也不代表它属于当前任务。范围先划清，再谈模型怎样理解资料。

**检测**发生在行动中和完成后。dsh-ctm 的有效性标记是一种检测——它不判断内容对不对，但帮人缩小"哪些内容可能有问题"的范围。写作管道里的审核节点是另一种检测：另一个模型读初稿，按标准给出通过或不通过的判断。契约校验检查输出结构是否符合约定。这些检测各有边界：有效性标记是启发式的，审核模型的判断也可能错，格式合规不等于内容成立。要把这些结果作为检查线索，并保留进一步核对的入口。

**恢复**发生在出错之后。局部重试是最简单的：一次工具调用超时，再试一次。撤销是另一种：dsh-ctm 里删错了内容，可以撤回操作。记忆库的进化整理在应用前做快照，验证不通过就整体否决，出了问题从快照恢复。但恢复不只是重试和撤销。更常见的情况是降级：可选服务不可用时，主流程跳过它继续走；记忆服务挂了，写作管道打个警告接着跑。还有一种恢复是停下来交还给人——审核超限后不伪装成质量合格，而是把遗留问题附在确认页上，让人来判。

这三层不是每个项目都已实现每一格。它们是一个检查框架：设计一个新功能时，问自己"行动前能限制什么、行动中能检查什么、出错后能怎么收场"。

一个 Agent 可以在循环中完成很多步骤。任务复杂以后，也可以把性质不同的工作拆开：有人专门组织结构，有人搜资料，有人写稿，有人检查。拆分提供了更明确的职责，同时引入了交接、验收和协调的问题。下面用我的写作管道说明这些问题。

## 第二编：多个 Agent 怎样分工并可靠交接

多 Agent 编排要设计两件事：各自负责什么，以及工作怎样交到下一位手里。单个节点完成得不错，整条流程也可能失败。资料搜得很全，写手却拿不到作者原意；审核指出了错误，下一轮改稿又把意见遗漏。这些问题发生在分工之间。

我做的[写作管道](https://github.com/ac0033/writing-agent/blob/main/README.md)把技术文章的生产拆成定框架、搜资料、写初稿、审核、润色五个主要角色。当前本地版本还在润色后做成稿核验。角色未必对应不同型号的模型，也不需要像一群人那样彼此闲聊。这里更实际的含义是，每个角色拿到适合自己的材料、工具和工作要求，由程序组织它们协作。

当前本地流程可以这样读：

```
定框架 → 大纲确认 → 搜资料 → 写初稿 → 审核 → 润色 → 成稿核验 → 成稿确认
  ↑        │        ↑        │       │                               │
  └─反馈───┘        └─补资料──┘       └─不通过：返回写初稿             │
                                                                     │
        内容修改：返回写初稿；表达修改：返回润色 ←─────────────────────┤
                                                                     └─同意 → 保存本地
```

保存之后，发布还有独立步骤：展示发布预览，再取得发布同意。补资料和审核返工都有次数上限；超限进入人工检查时，质量问题仍然保留。

### 先确定依赖，再决定怎么分工

写作里有些依赖很明确。先知道文章要说明什么，才能有针对性地找资料；写手需要大纲和材料；审核要看到稿件；润色需要知道哪些内容应该保留。这部分适合串行，前一步交付之后，下一步才开始。

有些工作可以独立开展。假设一篇文章需要核实上下文管理和任务调度两类资料，可以分别查找，最后汇总。独立搜集适合并行，但汇总仍要检查两边是否用了同一套定义、是否把不同版本的实现当成同一个版本。并行节省等待时间，也增加了汇总工作，不能只看同时启动了多少个节点。

当依赖复杂起来，可以把它画成一张关系图。假设大纲确认后，两路研究同时开始，写稿等待两路材料到齐；引用检查和表达检查又可以在稿件完成后各自进行。把“哪些结果是下一步的前提”画清楚，就得到一张依赖图。没有反馈回路时，这类图常被叫作 DAG，也就是不会沿箭头走回原点的有向图。术语背后只是一个朴素要求：前提没准备好，后面的步骤先别动。

还可以用任务分解树表达“一个问题由哪些子问题组成”，与执行依赖图配合阅读。按父问题指向子问题画出的有向树，是 DAG 的一种特殊形状，本身没有回路，但它表达的首先是分解关系，不是所有实际执行依赖。这种方式适合从一个大问题逐级拆出子问题，例如先分成几章，再为每章安排材料核查和写作。它让负责人知道各分支由谁完成，却不意味着分支天然互不影响。两章如果要解释同一个概念，仍需要统一定义；两个分支都要改同一份文件，也仍然需要协调。

还有反馈循环。我的管道允许写手在材料不足时请求补充资料，也允许审核把不合格稿件退回修改。循环要同时回答“什么情况下返回”和“什么时候停止”。当前配置给补充资料和审核返工都设了上限，避免意见反复来回却没有实质进展。这些是我项目已采用的串行和反馈方式；并行、复杂依赖图和树状拆分是可以按任务选用的组织方法，不代表当前写作管道全部实现了一遍。

### 每个节点要交付什么

定义节点时，先写清楚四件事：职责、输入、输出、验收标准，再决定给它什么工具。例如审核角色要检查论证和事实；它需要作者原材料、大纲、稿件和证据；它应交付通过或不通过的结论，以及能够据此修改的问题；只说“有待提高”不算有用的审核结果。

输入要跟着职责走。我的写稿节点除了大纲和搜索资料，也直接收到作者原材料。大纲是压缩过的结构，未必保留所有经历和限制；如果只交一份大纲，模型容易用看似合理的故事补空白。原材料一起传下去，才能让写手核对哪些是作者实际表达，哪些只是可以提出的推断。

输出也需要明确的交接格式。管道把处理说明与正式结果分开保存，下游主要使用正式结果，过程记录供回查。程序检查约定的结构是否完整，格式不合要求时只做有限修复，仍不合格就停在该节点。格式检查解决的是“下一步能否正确读取”，内容审核解决的是“读取到的结论是否成立”。二者不能替代。

### 状态是协作双方共同看的工作记录

如果每个角色各记一份进度，很容易出现写手认为稿子已改、审核员却还在看旧版的情况。我的管道用一份共享状态记录大纲、材料、稿件、审核意见和循环轮数。节点完成后返回自己的更新，由流程把它合并进去。

目前各节点按实现中的职责更新字段：写手更新稿件，审核角色更新结论和意见。这是程序的组织约定，不能因此宣称节点处在彼此隔离的权限沙箱里。若以后引入能自行操作共享存储的独立 Agent，还需要额外限制它们能改哪些内容。

有了并行，版本关系就更重要了。假设两位审核员分别检查同一篇稿件，反馈应说明针对哪一版；写手已经把稿件改过，再把旧反馈直接贴上去，可能删掉刚修好的内容。一个可行的设计是让反馈绑定稿件版本，合并前检查对应关系，冲突交给明确的负责人处理。不能用“大家共享状态”来掩盖谁先写、谁覆盖了谁。

通信方式也应跟着实际边界选。在我的写作管道内部，节点通过同一进程中的状态交接；对外接入记忆等服务时，才通过服务接口请求相应能力。MCP（Model Context Protocol，模型上下文协议）可以承载这类工具和服务接入，但节点协作是否清楚，最终仍取决于传什么、如何解释、失败后怎么办。换一种通信协议不会自动补上这些约定。

### 协作也需要预防、检测和恢复

协作层的预防，首先是缩小错误传播的范围。交给下游的材料要有来源和用途，外部网页里的话不能被当成流程指令，工具调用要有次数和资源上限。只给相关材料，也更容易看出某个错误究竟来自哪里。

检测则要看节点之间能否对得上。稿件有没有偏离大纲，引用能否支持对应句子，润色有没有改变数字和条件，都不能仅凭某个节点说“完成了”来判断。我的本地管道在内容审核之外，还检查润色前后的一些变化，并在成稿核验中把论断与读到的原文对应起来。模型审核仍可能漏错，能用程序精确核对的格式、链接和原文片段，就让程序核对；无法据此确定的内容继续保留为问题。

多个审核者也不是越多越保险。如果他们拿到相同的错误资料，很可能一致赞同错误结论。比简单数赞成票更重要的是检查依据：一位检查作者原意，一位核对来源，另一位检查表达是否改变条件，各自给出可回查的理由。这样的分工才可能提供不同角度。这是协作设计可以采用的办法，并非我的管道已经配置了多个投票审核员。

恢复需要能回到合适的位置。我的管道保存检查点，重新接续同一个会话时，可以从未完成的节点继续，不必重跑全部已完成节点。它恢复的是流程状态，并不自动撤销已经发生的外部操作。一个节点如果已经发布内容，之后再重跑它，仍可能造成重复发布。因此写入和发布这类动作还要有自己的记录、重复请求处理和授权检查。

流程结束也有不同含义。审核返工达到上限后，本地实现保留“不通过”和具体问题，继续整理成可供人查看的稿件，并不会把失败改为通过。大纲确认和最终成稿确认是图中的两个人工节点；文章确认并保存后，发布还要另行展示预览并取得同意。发布预览绑定目标和正文版本，内容改了，原来的授权不能继续沿用。这里描述的是本地版本，公开仓库的较早版本尚不能代表这些保护已经全部发布。仍有质量问题的稿件可以经人确认后保存在本地，但当前发布入口会阻止它进入发布。

最终确认时，人可以指出内容或表达问题，分别把稿件交回写稿或润色环节。人的介入由此有了明确位置：不必代替每个节点操作，却能改变方向、接受或拒绝遗留问题，并决定是否公开。

### 成本、可见性与持续改进

拆分以后，成本既来自模型调用，也来自检索、等待和返工。当前配置中，定框架使用 DeepSeek 的 pro 型号，研究和审核使用 flash 型号，写稿和润色使用千问。这样的分工分别关注结构与观点、材料与规则检查、文字与表达。它是当前配置的设计选择，不能当作不同模型能力的实测排名。是否保留这样的分工，要看节点能否完成职责，以及增加一次调用能否带来值得的改进。

预算也应覆盖整条任务。某个节点的调用次数有限，不代表所有节点相加后的时间和费用仍可接受。任务可以预先约定检索次数、返工轮数、时间与费用边界；接近边界时，停止低价值尝试，保留已有产出和未解决问题。当前项目已有局部工具与循环预算，整条系统的统一预算管理还需要进一步设计。

透明和直观在这里是同一件工作中的不同要求。底层要保留节点状态、交接材料和错误记录，界面则要让人看懂“哪一步已经完成、卡在哪里、接下来需要什么决定”。我的管道提供节点进度和调用状态，但日志仍只是基础；让不熟悉实现的人看懂整条过程，是我对这类工具的持续要求。

失败记录的用途也不止排错。反复出现的问题，应先区分是资料不足、模型能力不足、交接丢失、工具返回不清楚，还是验收标准本身不合理，再改对应环节。修改后用同类任务检查，确认原问题改善且没有引入新问题。不能每次失败都只给提示词加一句“请更认真”。

这套写作流程已经把单个 Agent 的信息、行动和保障机制扩展到角色之间，但主要步骤仍由程序预先安排。下一步有两个相连的问题：任务路径写不全时，谁根据反馈调整步骤；连任务本身都还没有被人提出时，系统能否主动发现它？前者需要自主规划，后者把我们带向 AI OS。

## 第三编：让 AI OS 主动发现问题，把改变交给有依据的选择

### 从完成任务，走向主动发现值得做的事

固定工作流适合步骤比较清楚的任务。需要根据环境决定下一步时，自主 Agent 会在执行中调整路线。例如修改代码，先读相关文件，形成修改方案，再运行检查；检查失败后继续找原因，调整修改范围，缺少必要条件则停下来说明。这里的自主性，体现在根据实际结果改变做法。

这与用了几个 Agent 是不同的维度：一个 Agent 也可以自主规划，多个 Agent 也可以沿固定流程工作。Anthropic 在[《Building effective agents》](https://www.anthropic.com/engineering/building-effective-agents)中区分了由预定代码路径组织的工作流，以及由模型动态决定步骤和工具使用的 Agent。本文从固定分工走向自主规划，沿用的是这种控制路径上的区别。

我在演变笔记里特别保留了“识别失败、调整策略”。模型说检查过，不等于工具真的运行过；检查返回成功，也不等于完成了用户的目标。因此，自主规划仍需要可操作的完成标准、能辨认成败的工具结果，以及预算和停止条件。搜资料时允许模型调整关键词，发布文章时保留固定确认，这两种组织方式可以放在同一系统里。

自主 Agent 通常仍从一项被交付的任务开始。再向前一步，系统能不能自己发现“有件事值得处理”？比如，文章还没进入终稿核验，它就发现某条关键来源可能失效；流程还没明显卡住，它就发现多个节点重复读取同一批资料，提出减少重复工作的办法。这里增加的能力，是持续观察、提出问题和提前准备选择。

**本文采用的 AI OS 构想，是叠加在传统操作系统与应用层之间的自主管理器（Autonomic Manager）。它的主要价值是预测、调度、优化和排查隐患，让有用的想法出现在人的要求之前，也覆盖人尚未想到的角度。**传统操作系统继续负责资源分配与底层隔离，应用层及其中的人工确认继续负责实际执行。AI OS 可以建议何时检查、先试什么、哪些工作值得合并，但不会因此接管操作系统的资源裁决，也不会绕过应用的执行入口。

这个分工很具体：它发现一个问题，读授权范围内的证据，在副本里试验，把可审查的提案交出来；执行改变的应用再按授权落实。下面是我目前采用的设计，还没有把现有项目打通成完整 AI OS。记忆、知识库、写作管道和上下文插件可以提供部分基础，但主动发现问题是否有价值，仍需要真实工作流来验证。

### 随机性与选择机制：多想一些，让证据决定留下什么

假设写作流程变慢了。一次生成可能只想到“换一个更快的模型”；换个观察角度，还可能想到检索重复、传入材料过长、工具调用在重试，或者某个节点的验收要求不清楚。对主动排查来说，能产生不同解释是有用的：人在熟悉的流程里，也可能长期只检查同一类原因。

我把这部分设计概括为：**随机性与选择机制配对，才可能成为有用的主动性。**模型负责产生候选假设，验证机制负责淘汰站不住的假设，人负责判断剩下的改进是否值得采用。“随机性 × 选择机制”在这里表达两者的依赖关系，不是一条已经测量过的数学定律，也不意味着采样越随机越好。

模型可以多次采样寻找分歧，也可以分别从运维、产品、安全和用户角度检查同一现象。不同角色的用途是扩大问题覆盖面，不能用几个角色意见一致来代替证据。每个候选都要交代依据与检验方法；只有“也许还能优化”这样的想法，不值得进入实验和人工审查。

选择层则需要明确、可执行的条件：假设怎样算被否定，实验比较什么，什么结果允许形成提案，谁有权接受。检查程序可以确定地执行规则，但规则本身仍可能漏掉关键条件；模型给出的评价也仍然可能错。这里要求的确定性，是门槛不能随一次生成的偏好改变，失败不能被包装成成功，越过门槛必须留下依据。

所以，这个构想的原则是：**让模型在没有生产写权限的地方充分提出想法，让选择条件严格执行，让信任按证据逐步扩大。**“想法在人之前”是希望达到的效果，不是对模型洞察力的保证。真正要比较的是它发现了哪些有用问题、提前了多久，以及为此消耗了多少实验资源和人的注意力。

### 执行与自治分成两个回路

要给主动性留下空间，又防止一个未经证实的想法直接改变工作环境，首先应把执行回路和自治回路分开。

| 回路 | 从哪里开始 | 可以做什么 | 怎样进入真实改变 |
|---|---|---|---|
| 执行回路 | 人提出需求，或接受一份提案 | 在授权范围内通过应用完成任务，必要时写入生产环境 | 按相应审批和执行规则推进 |
| 自治回路 | 系统主动观察并提出假设 | 读取获准的信号，在受限沙箱中实验，形成提案 | 自身没有生产写权限；提案被接受后交给执行回路 |

这里的生产环境，就是正在使用的真实文件、数据和服务；沙箱则是可丢弃的实验环境。两个回路可以共享模型、工具实现和技能库，但拿到的凭证、目录挂载和可调用动作必须不同。执行回路有一项写入工具，不意味着自治回路也能使用相同的写入身份。

这条界限要由操作系统、容器和工具服务强制落实：只读挂载限制原文件修改，非特权容器与隔离环境承载实验，凭证限制服务访问。提示词中的“不要修改正式数据”和工具调用前的检查可以补充规则，但不能独自承担隔离。自治回路可以在沙箱里写文件、运行实验，这与它对生产只读并不冲突。

只读也不是没有代价。读取本身涉及信息权限，实验会花费时间和费用；若沙箱能任意访问网络或调用外部服务，也可能造成影响。因此，自治回路还需要限定数据范围、外部连接、调用额度和运行时间。达到额度就留下结果并停止，不能为了验证一个想法无限试下去。

执行回路同样可以拒绝提案。发现异常、实验成功、批准改变，是三个不同状态。自治回路把证据准备充分，执行回路再检查目标、版本和授权；只有被接受的部分进入真实操作。前面写作项目把成稿确认与发布确认分开的做法，正可以帮助理解这里的交接。

### 五个组件：把一个猜测变成可审查的提案

自治回路可以按五个组件组织：

```
感知 → 认知 → 验证 → 提案 → 治理
       ↑                    │
       └──采纳、拒绝、修改的反馈──┘
```

它们不一定是五个独立 Agent，而是五类职责。为了看清每一步交付什么，下面沿用一个尚未自动实现的知识库维护场景：系统发现一些笔记引用的网址访问失败，需要判断是否值得修复。

**感知：收集信号，先说明看见了什么。**工作流可以暴露三类只读信号：事件流记录发生了什么，例如检索失败、任务重试；指标流反映变化，例如耗时、调用次数和输入用量；内容流提供解释线索，例如日志、文档和工单。需要读取对话时也只能使用明确获准的范围，不能因为技术上读得到就全部收集。

在这个例子里，感知组件记录哪些网址访问失败、何时发生、重试结果如何，以及哪些笔记引用了它们。这只能证明访问异常，不能证明笔记已经过时。临时网络问题、页面迁移、来源撤回，都还只是待核查的解释。平台签发的只读凭证决定能观察什么，“观测即权限”首先要求把观察边界写清楚。

**认知：提出可以被否定的假设。**模型可以问：机构是否调整了网站目录？是否只有特定网络环境访问失败？同一来源是否已有更新版本？即使没有明确报警，也可以主动检查某个关键流程最可能在哪一步出问题。

产出要整理成“假设卡”，包括假设陈述、已有依据、可证伪的检验方法和影响量级。例如：“可能是站点迁移；依据是同域名多个旧地址同时失效；到官方站点核对标题、作者、版本和正文，若找不到匹配则保留未证实；影响范围是引用这些页面的笔记及正在使用它们的稿件。”没有检验方法，就先停在认知层；影响大小暂时无法判断，也要写明。

**验证：在沙箱副本里检验，保留与真实环境的差别。**设计草案把这个环境称为“沙箱孪生”：用容器、脱敏数据和模拟依赖建立可丢弃副本，尽可能重现待检查的工作。它的作用是让试错不直接改变正在使用的数据，并为重复实验提供条件。

查找新网址时，找到同名页面只算线索；版本和正文变了，还要检查原笔记中的论断是否仍被支持。若进一步测试一种自动修复方法，应在运行前约定样本、对照方法和判定阈值，记录误替换、漏检和耗时，防止看到结果后再挑有利标准。一次找到新地址是一次核验，不能冒称已经验证了整体方法的性能。

实验报告还要声明保真度差异：哪些数据经过脱敏，哪些服务用了模拟返回，哪些问题在副本里无法重现。沙箱能运行，不等于生产环境一定有效。证据不足或者预算用完，就保留未解决项，不把猜测填进“验证通过”。

**提案：把证据、收益和影响整理成一次明确选择。**在这个构想中，提案是自治回路向应用层请求改变的唯一出口。它应列出可回溯的证据链、拟修改的位置、预期收益及测量依据、影响范围、回滚方案和置信度等级。

针对网址维护，提案要区分已经确认的地址迁移、疑似内容变化和暂时无法访问，并展示具体修改差异。影响范围说明哪些笔记会变、是否涉及待交付的稿件；回滚方案说明原版本怎样保留、修改失败怎样恢复。没有测量过的收益可以作为待检验目标，不能填成已经节省了多少时间。置信度也应解释来自哪些核验步骤，不能只附模型随口给出的百分比。

提案还要遵守三个交互条件：不催促、不擅自执行、被拒后没有新证据就不重复提交。急迫的问题可以在打扰预算内实时提示，普通维护建议合并进日报。它交给人的应当是可以直接审阅的一份选择，而不是让人从零重新调查的模糊告警。

**治理：作出决定，让反馈改进下一轮认知。**人像审查代码变更一样查看提案，核对证据、差异和影响，可以接受、拒绝或要求修改。提案会处理不可信的网页和日志，其中可能夹带诱导系统越权的内容；提案通道本身也要接受审查，来源中的指令不能随着摘要获得执行权。

被接受的内容交给执行回路，按确认的目标和版本落实，执行后再检查。如果文件已经改版，原提案需要重新核对。被拒绝的内容保留原因：证据不足、收益有限、时机不合适，分别对应不同的后续改进。不能把“现在不做”当成“这个问题永远不重要”。

这些采纳、拒绝和修改记录，可以先用于调整提示、排序和评价规则；积累足够可靠的数据后，再考虑用作偏好或奖励模型的训练材料。这是设计方向，并非现有项目已经具备自动训练与自我进化能力。系统可以提出修改治理规则的建议，生效仍要经过授权。

### 信任阶梯：逐步增加报告和实验能力

双回路划清的是不能越过的权限边界，信任阶梯回答的是：在这个边界内，什么时候允许系统更主动、更频繁地参与工作？设计草案给出了 L0 到 L4 的安排：

| 等级 | 开放的能力 | 应当先看到的证据 |
|---|---|---|
| L0 观察员 | 只读观察、静默归档 | 默认起点，先检查读取范围和记录质量 |
| L1 报告员 | 定期日报或周报 | 经过一段试运行，抽检确认报告有价值 |
| L2 建议者 | 在预算内实时打断 | 提案质量稳定，没有重大误报 |
| L3 实验员 | 更高的沙箱实验配额 | 实验结论能够复现，资源消耗受控 |
| L4 准自治 | 明确规则下，低风险变更默认批准且可撤回 | 长期记录、可回滚性和双人授权 |

这里的 L4 需要与双回路一起理解：增加的是执行回路中经过预先授权的低风险动作范围，自治回路仍只有生产只读与沙箱实验权限。默认批准必须限定对象、动作和条件；超出条件仍要逐项审批。它不能把一次提案被采纳，扩展成自治回路永久获得生产写权限。

设计草案为试验提出了两周观察、提案采纳率至少 60%、实验复现率至少 80% 等候选门槛。这些是待验证的初始设置，既不是实测成绩，也不是行业标准。业务风险、样本数量和审查能力不同，门槛也需要调整。开放能力以后仍要持续检查，出现越界、误报或无法复现的结论，应能降级或收回授权。

阶梯上的“更可信”不等于“更少记录”。越接近真实改变，越要清楚展示依据、影响和回退办法。透明帮助人审核，直观帮助人快速判断，自动化才有机会逐步扩大，而不是用更多通知把工作重新交回人。

### 怎样判断主动性值得保留

评价 AI OS，不能只数它主动运行了多少次、生成了多少建议。这个构想关注五项指标：

| 指标 | 要回答的问题 | 如何避免误读 |
|---|---|---|
| 提案采纳率 | 提交的建议中，有多少值得采用？ | 区分拒绝原因；被采纳也不等于事实正确 |
| 隐患漏检率 | 后来确认的问题中，有多少没有提前发现？ | 结合人工抽查和事后回看，不能仅用已发现问题计算 |
| 平均发现提前量 | 相比人工发现或已有告警，早了多久？ | 记录两个时间点；没有对照就不能宣称提前 |
| 实验复现率 | 同样条件下，结论能否再次成立？ | 同时记录环境差异，避免只重跑容易成功的样本 |
| 打扰成本 | 人为这些建议花了多少审查时间？ | 同时关注误报、重复提交和通知次数 |

提案采纳率可以作为提案质量的运营指标，但严格说来不等于统计意义上的精确率：一条正确建议也可能因为成本太高被拒绝。隐患漏检率同样只能在可核查的问题集合上估计，未知问题不会自动出现在分母里。这份设计用这些指标表达方向，落地时还需要明确计算口径。

我在这个设计中优先控制低价值打扰。主动系统如果把所有猜测都交给人筛，人很容易不再看它。宁可先做筛选、补实验，再交出少量有依据的提案。这个取舍也不能机械套到所有场景：影响重大的隐患仍需要合适的报告规则，不能为了让采纳率好看而保持沉默。

调度因此包括两件相关的事。一是安排观察和实验的顺序：影响当前交付的来源核查，可能先于例行旧链接维护；重复检查同一公开来源，可以考虑共享已核实的结果，并保留时间与版本。二是安排何时请人决定：实时打断设上限，超出后转入定期报告；被拒且没有新证据的提案继续归档。AI OS 可以优化这些工作安排，实际资源额度和访问边界仍由底层平台执行。

### 从一个真实工作流开始验证

落地时，我会先把这套构想缩到一个工作流：定期生成假设卡，在沙箱里验证少量候选，把提案写进固定目录供人审阅。设计草案中的初步方案是，用 Kimi Code CLI 配合定时运行完成试验；调用前的 Hooks 用于检查和阻断不合条件的操作，真正的只读与隔离仍落到挂载、凭证和容器设置上。两周作为初始观察周期，再根据提案质量与审查成本决定是否继续。

完整形态的候选方案，是以 DeepSeek Harness 作为运行底座，把感知、认知、验证、提案和治理组织成插件包；用轨迹记录保存证据链，用多角色 Agent 扩大假设来源，用技能库沉淀领域要求。日常扫描、深入分析和敏感内容处理，也可以选择不同模型，但具体路由要按能力、成本和数据边界验证。这些是实现设想，不代表现有插件已经具备这一整套能力。

最先要验证的，不是系统能否不停运行，而是它能否从真实信号提出可检验的问题，把坏想法挡在提案之前，并让人用较少的时间作出有依据的决定。只要其中一环没有成立，就应回到对应环节调整，而不是继续增加 Agent 数量或扩大权限。

从单 Agent 到多 Agent，再到这样的 AI OS，前一层的机制始终还在：模型需要合适材料，工具需要边界，结果需要检查，失败需要恢复。分工扩大后，要把这些要求接到交接与共享状态上；系统开始主动提出任务后，还要把它们接到假设、实验、提案和授权上。

dsh-ctm 让我从上下文的可见与可调切入；记忆和知识库处理信息怎样保留、更新和回溯；写作管道把角色分工、核验和人的决定接起来。这些实践为 AI OS 提供了具体的设计依据。接下来值得继续验证的，是在同样清楚的边界里，系统能否早一步发现有用问题，并把它整理成人愿意审、也能够判断的提案。
